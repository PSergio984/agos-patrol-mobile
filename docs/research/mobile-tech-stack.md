# Mobile Tech Stack Research — agos-patrol

Date: October 2026. Audience: solo dev, React/TypeScript + Python, limited native mobile experience.

## Recommendation

**Use React Native with Expo (managed workflow, SDK 57+).** Rewrite the app's UI layer as React Native primitives while porting the business logic — axios client + interceptors, contexts, WebSocket layer, i18n dictionaries, offline-queue algorithm, phone/format utilities — largely as-is. Use `expo-notifications` for push and have the FastAPI backend send via the **Expo Push Service** (a single HTTPS POST, no Firebase server SDK required) while keeping `pywebpush` for PWA users.

Runner-up: **Capacitor** (wrap the PWA). Lowest initial effort — ~100% of the codebase survives — but it still forces the same backend push rework (there is no Push API inside Capacitor's WebView), leaves you with a WebView ceiling for future native features, carries an App Store "minimum functionality" review risk, and is harder to evolve past. It is the right answer only if the goal is "a store listing within a week" rather than "a native app."

Flutter and fully-native Kotlin/Swift are rejected: Flutter is a from-scratch Dart rewrite with zero code reuse, and dual native codebases are unmaintainable for a solo dev.

**Scope note:** this app has **no geolocation, no maps, and no device-camera usage** (verified by scanning `src/` — "camera" refers to backend-fetched waterway snapshots via `GET /…/latest-frame` plus `camera_update` WS messages). That removes the usual hardest native APIs from the port entirely.

### agos-backend

- REST under `/api/v1` (`app/api/v1/router.py`), WebSocket at `/ws` (`app/api/v1/endpoints/websocket.py`, `app/services/websocket_service.py`).
- Push is **Web Push only**: `pywebpush==2.3.0` + `py-vapid==1.9.4` (`requirements.txt`); `GET /push/vapid-public-key`, `POST /push/subscribe` (`app/api/v1/endpoints/push.py`); subscriptions stored as `{endpoint, p256dh, auth}` (`app/models/responder_related/push_subscription.py`). **No FCM/APNs code exists.**
- ⚠️ Existing bug found during research: `notification_service.send_push()` sends only `{title, message}` (`app/services/notification_service.py:234-237`). The service worker's `data.type` and `data.url` are never populated, so per-severity vibration patterns in `sw.js` are dead code — every push falls back to the "announcement" pattern. A native port should fix this by putting `type` in the push payload and mapping it to Android notification channels.

| Criterion                      | React Native + Expo                                                                             | Capacitor (wrap PWA)                                                                       | Flutter                                                 | Native Kotlin/Swift                                   |

| **Push path**                  | FCM/APNs via `expo-notifications`; Expo Push Service or direct FCM/APNs                         | FCM/APNs via `@capacitor/push-notifications`                                               | FCM/APNs via `firebase_messaging`                       | FCM / APNs directly                                   |
| **Backend push work required** | Yes — new token type + sender                                                                   | Yes — same                                                                                 | Yes — same                                              | Yes — same                                            |
| **Per-severity vibration**     | Android channels w/ `vibrationPattern` (iOS: not possible — same as today)                      | Android channels via FCM `channelId` (same iOS limit)                                      | `flutter_local_notifications` channels                  | Full control                                          |
| **WebSocket**                  | Built-in `WebSocket`, foreground only (same as web)                                             | Browser `WebSocket` in WebView                                                             | `web_socket_channel`                                    | Native clients                                        |
| **Offline storage**            | `expo-sqlite` / AsyncStorage / `expo-secure-store` (tokens)                                     | localStorage survives, but WKWebView storage can be evicted → use `@capacitor/preferences` | `sqflite`/`shared_preferences`/`flutter_secure_storage` | Room / Keychain etc.                                  |

| **Native ceiling**             | High — real native UI, escape hatch to bare RN                                                  | Low — WebView forever                                                                      | High                                                    | Highest                                               |
| **Store review risk**          | Normal                                                                                          | Apple Guideline 4.2 "minimum functionality" risk for thin wrappers                         | Normal                                                  | Normal                                                |

Key asymmetry: **every option requires backend push changes** — `pywebpush` speaks RFC 8291 Web Push, and none of the native paths can consume those subscriptions. Capacitor's effort advantage is therefore smaller than it first appears: you still do the backend work, but you keep the WebView ceiling.

### Backend changes required (agos-backend)

1. **New token storage** — `push_tokens` table (or column on a unified table): `{responder_id, token, platform(ios/android), kind(expo/fcm)}`. Keep `push_subscriptions` (VAPID) untouched — the PWA can keep living alongside the native app.
2. **New endpoint** — `POST /push/subscribe-native` (or extend `/push/subscribe` with a discriminated schema).
3. **New sender** — in `notification_service.send_push`, branch on subscription kind. Expo path: `httpx.post("https://exp.host/--/api/v2/push/send", …)` with `{to, title, body, data: {type, url, alertId}, channelId: type, priority: "high" for critical}`. Then poll `getReceipts` ~15 min later and prune tokens on `DeviceNotRegistered` (replaces today's 410-Gone handling). No Firebase server SDK needed for this path.
4. **Include `type` (and a deep-link `url`) in the payload** — fixes the dead-vibration-pattern bug for both web and native.
5. Optional later upgrade: bypass Expo Push Service by minting device tokens (`getDevicePushTokenAsync`) and sending via `firebase-admin` (Python, official) + APNs — needed only if you want SLA-adjacent control or FCM-only features.

## Migration effort estimate

Rough order for a solo dev, part-time: **3–6 weeks** to feature-parity beta.

- **Days 1–3:** Expo scaffold (SDK 57/58), dev builds (push won't work in Expo Go on Android), EAS project, Firebase project for Android FCM credentials + Apple push credentials.
- **~40% of effort:** copy non-UI layer — API modules, interceptors (token source swap), contexts (WS backoff, auth gate, i18n, theme), utils, types, i18n dictionaries.
- **~50% of effort:** UI rewrite — ~35 components across Home (4 cards + frame modal + sparkline), Alerts (list + bottom-sheet ack form), Profile, Verify (phone + OTP), nav/layout. NativeWind keeps class names; budget extra for the wave gauge (SVG → react-native-svg) and the bottom drawer.
- **~10%:** backend — token table + endpoint + Expo-push sender branch (FastAPI + httpx; a day or two).
- Store plumbing: Apple Developer $99/yr, Google Play $25 one-time, EAS Build (free tier exists).

Keep the PWA deployed during and after — dual-send notifications let responders migrate at their own pace.

## Risks & trade-offs of the recommendation (vs Capacitor runner-up)

1. **Expo Push Service has no SLA** (stated in Expo docs). For a flood-response app this is the sharpest risk. Mitigations: send `priority: high`; check receipts; if reliability demands it later, switch the same client code to device tokens + `firebase-admin`/APNs without changing app architecture. Note the status quo isn't better — Web Push has no SLA either, and iOS web push additionally requires the app be installed to the Home Screen.
2. **UI rewrite is real work.** Capacitor would ship a store app faster, but you'd still owe the backend push work, then live inside a WebView: no native feel, WKWebView localStorage eviction risk on iOS, App Store 4.2 scrutiny, and a harder migration to real native later (you'd redo this same UI rewrite anyway). If you believe a native app is the destination, paying the UI cost once in RN is cheaper than paying it after a Capacitor detour.
3. **Expo Go can't do push on Android (SDK 53+)** — plan on development builds (`npx expo run:android` or EAS) from day one; adds build-time friction vs `vite dev`.
4. **SDK treadmill** — Expo ships 3–4 SDKs/year, ~1yr support window each; budget for periodic `expo install --fix` upgrades. RN itself is post-New-Architecture stable (New Arch mandatory since 0.82; 0.86/0.87 shipped without breaking changes).
5. **NativeWind version split** — v4.2.7 stable (Tailwind 3) matches your current Tailwind 3 setup; v5 RC (Tailwind 4) is not production-ready. Use v4, or skip NativeWind and use plain `StyleSheet` — your styling surface is small enough either way.
6. **iOS vibration parity** — custom vibration patterns were never possible on iOS (web or native); Android channels preserve today's Android behavior. No regression.
7. **WS only in foreground** — same semantics as the web app (WS reconnects on focus). Push covers killed-state delivery; no capability lost.
8. **New dependency: an Apple + Google store presence** — review cycles replace Vercel instant deploys; EAS Update provides OTA JS updates for store-compliant fixes.
